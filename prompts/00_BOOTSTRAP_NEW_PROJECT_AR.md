# برومبت 00 — إنشاء منصة المذاكرة من الصفر

أنت مهندس برمجيات Full-stack/AI مسؤول عن تأسيس مشروع قابل للتشغيل، لا مجرد كتابة خطة. لديك إذن بإنشاء الملفات وتشغيل الأوامر والاختبارات داخل workspace الحالي.

## الهدف
إنشاء هيكل مشروع جديد باسم `ai-study-platform`:
- `frontend/`: Next.js + TypeScript.
- `backend/`: Python + FastAPI.
- `docs/`: توثيق.
- `prompts/`: برومبتات التنفيذ.
- `PROJECT_STATUS.md`: سجل الحالة.

## قواعد لا تفاوض عليها
1. ابدأ بفحص المجلد الحالي وملفات Git، ولا تحذف أو تستبدل ملفات مستخدم موجودة.
2. إن لم يكن المجلد فارغًا، أنشئ مجلد مشروع فرعيًا أو اقترح مسارًا آمنًا بدل مسح الموجود.
3. تحقّق من إصدارات Node/Python/Git المثبتة. اختر أحدث إصدارات مستقرة ومتوافقة وقت التنفيذ، وثبّت الإصدارات في ملفات المشروع؛ لا تخترع أرقام إصدارات من الذاكرة.
4. اقرأ الوثائق الرسمية الحالية للأطر والمكتبات قبل اعتماد إعدادات متغيرة.
5. لا تطلب مفاتيح أو أسرار الآن؛ أنشئ `.env.example` فقط.
6. لا تستخدم بيانات وهمية لإظهار أن خدمة خارجية متصلة.
7. لا تضف Redis أو Docker أو queue framework أو agent framework دون حاجة مثبتة.
8. لا تنفذ أوامر مدمرة أو تنشر شيئًا على الإنترنت دون موافقة.
9. بعد كل مجموعة تغييرات شغّل الاختبارات المناسبة وأصلح الأخطاء قبل المتابعة.
10. لا تكتفِ بعرض snippets؛ أنشئ الملفات فعليًا في workspace.

## خطوات التنفيذ
A. فحص البيئة والمجلد:
- اعرض المسار الحالي، الملفات الموجودة، إصدارات Node وnpm وPython وGit.
- لا تطبع أي أسرار إن وجدت.
- حدّد مدير الحزم وفق lockfile؛ إن كان مشروعًا جديدًا، اختر npm ما لم توجد ضرورة موثقة لغيره.

B. إنشاء frontend:
- أنشئ Next.js App Router مع TypeScript وlinting حسب إعدادات الإصدار الحالي.
- صفحة رئيسية بسيطة بالعربية RTL تحمل اسم «منصة المذاكرة الذكية».
- صفحات placeholder واضحة لتسجيل الدخول ولوحة الطالب والمواد، لكن لا تدّعِ أن المصادقة تعمل بعد.
- ملف API client يقرأ `NEXT_PUBLIC_API_BASE_URL`، ويتعامل مع timeout وHTTP errors دون تسريب بيانات.
- `.env.local.example` أو `frontend/.env.local.example` وفق الهيكل المختار.
- لا تضع Gemini أو Cloudinary secret أو DATABASE_URL في frontend.

C. إنشاء backend:
- FastAPI بتقسيم بسيط `app/main.py`, `app/core/config.py`, `app/api/routes/health.py` واختبارات.
- استخدم settings validation؛ إذا كانت قيم الخدمات غير موجودة، يجب أن يوضح endpoint readiness حالة `not_configured` دون كشف القيم.
- أضف `/health/live` للـ liveness و`/health/ready` للجاهزية. لا تجعل liveness يعتمد على الخدمات الخارجية.
- أضف CORS يسمح فقط بالأصول المعرّفة في environment.
- أضف `GET /api/v1/meta` يعرض اسم التطبيق وإصدار API فقط.
- إعداد logging لا يطبع headers أو secrets.
- أنشئ `backend/.env.example`, `requirements.txt` أو pyproject مناسبًا، وpytest config.
- لا تنفذ JWT auth يدويًا بشكل بدائي؛ اترك integration point موثقًا للمرحلة التالية.

D. هندسة البيانات:
- أضف Alembic وSQLAlchemy dependencies فقط، لكن لا تضع migrations غير مدروسة قبل المرحلة 03.
- جهّز docs يشرح فصل Supabase Auth عن Neon DB.
- لا تضع أي أسرار في ملفات الأمثلة.

E. جودة المستودع:
- `.gitignore` يستثني `.env*` مع السماح بـ `.env.example` و`.env.local.example`، و`node_modules`, `.next`, `.venv`, cache/logs.
- README عربي يشرح المتطلبات، الإعداد، أوامر التشغيل والاختبار.
- وثّق architecture وقراراتها.
- حدّث `PROJECT_STATUS.md`.

F. التحقق:
- شغّل تثبيت dependencies إذا أمكن دون تعديل global environment.
- شغّل اختبارات backend، lint/typecheck/build للواجهة حسب المتاح.
- اختبر health endpoints محليًا إن أمكن.
- إذا تعذر تثبيت dependency بسبب الشبكة/الصلاحيات، اذكر الأمر والخطأ بالضبط ولا تدّع نجاحه.
- لا تبدأ ربط الخدمات الخارجية في هذه المرحلة.

## معايير القبول
- frontend وbackend موجودان ويعملان محليًا وفق README.
- health/live وhealth/ready يتصرفان بصورة صحيحة.
- لا توجد أسرار committed أو داخل ملفات frontend.
- الاختبارات الأولية ناجحة أو موثّق سبب تعذرها.
- `PROJECT_STATUS.md` يذكر الحالة الحقيقية والخطوة التالية.

4. الاختبارات التي نُفذت ونتائجها الفعلية.
